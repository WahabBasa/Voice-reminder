## Reminder scheduling + model reliability overhaul (unified schedule) - (20:30)

**Status**: ✅ Landed end-to-end (app + Convex). Core scheduling works for once/interval/weekly patterns; remaining work is STT language forcing + deeper RRULE/timezone correctness.

This work was prompted by:
- Log spam (`pending_get id=null`) obscuring real issues
- Inconsistent reminder creation from the model for anything beyond simple “once at HH:MM”
- Interval reminders not supporting 5m/1h reliably (and previously clamped to 15m)
- Alarm audio sometimes double-starting
- Confusing behavior when a computed trigger time ended up “in the past” (the old safety net scheduled `now + 5s`, causing immediate fires)

### High-level outcome

1) **Unified schedule representation**
- Canonical schedule types:
  - `once` → absolute `onceAt` (ms)
  - `interval` → `intervalMs` + `anchorAt` (ms)
  - `rrule` → RFC5545 RRULE string + `dtstart` (+ optional `until`, `tzid`)
- Local store reminders now carry these fields (`schemaVersion: 4`).
- Notifee notification payload now includes schedule fields so rescheduling is deterministic after `DELIVERED`.

2) **Convex action becomes the “normalizer”**
- Convex now coerces/repairs the model output into deterministic fields (and collects `parseWarnings`).
- Interval constraints updated to **min 5 minutes**, max 365 days.
- If model returns contradictory values (e.g. provides `days` but frequency not “custom”), Convex forces the correct interpretation.

3) **Safer scheduling behavior**
- For “no future occurrence” cases (expired once reminders, bounded recurrences that ended), scheduling now **skips** instead of “now + 5s”.
- Startup sync treats “no future occurrence” as “skipped”, not “failed”.

4) **Audio stability**
- `ensurePlaying()` prevents alarm audio double-starting (common when overlay mounts quickly after native playback begins).

### Important product semantics discovered

**Interval reminders are treated as a fixed cadence anchored at `anchorAt`, not “wait N minutes after creation”.**

Example: user says “every five minutes from now”.
- Convex returns `intervalMs=300000` and `anchorAt=Date.now()` (Convex clock).
- Next occurrence is the smallest `anchorAt + k*intervalMs` that is `> now`.
- If creation completes close to the next boundary, the first fire can be < 5 minutes (e.g. 1 minute), then subsequent fires follow the 5-minute cadence.

Decision: **leave as-is for now** (accepted behavior).

### What was implemented (details)

#### A) Scheduling engine (new)

- Added `lib/schedule.ts`:
  - `ScheduleType`: `'once' | 'interval' | 'rrule'`
  - `getNextOccurrence(schedule, referenceTime)` (dispatch)
  - `normalizeSchedule(...)` applies constraints and emits warnings
  - `migrateLegacySchedule(...)` converts legacy `{time,date,frequency,days}` into the new schedule where possible
  - `tryParseScheduleFromText(...)` fallback heuristics (e.g. “every N minutes”, “every Sunday at 8am”)

Dependencies:
- Added `rrule@^2.8.1` to `package.json` (RFC5545 recurrence parsing/building)

#### B) Notifee scheduling/rescheduling updates

  - Removed `pending_get ...` spam in `getPendingAlarm()`
  - Kept a safety net for recurring reminders if computed trigger ends up in the past (still adjusts to `now + 5s`), but now **avoids this for one-time reminders**
  - Reschedule logic after `DELIVERED` prefers unified schedule; falls back to legacy schedule

#### C) App wiring + schema migration

#### D) Convex parsing/normalization improvements

- `convex/actions.ts` (`actions:processVoiceReminder`):
