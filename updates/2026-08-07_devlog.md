# Devlog - 2026-08-07

## iOS bring-up: first builds, white screen, Sentry, two audio fixes - (02:00-11:00)

**Status**: ✅ App runs on iPhone 12 (iOS 26); foreground alarms speak; observability live

Apple dev account approved, so today was iOS day. Config prep (bundle id, buildNumber, `ios: { sound }` blocks in the three notification payloads), `eas device:create`, first ad-hoc build installed OTA. Chain of fixes from there:

- **White screen on launch**: `.env.local` is gitignored so cloud builds had no `EXPO_PUBLIC_CONVEX_URL` — `new ConvexReactClient(undefined)` threw before React mounted. Registered the var as EAS env for all three environments. Same landmine was under the Android cloud build path.
- **Sentry** (org `oldowan`, EU): separate `voicereminder-ios` / `voicereminder-android` projects, DSN picked by platform in `lib/sentry.ts`, source maps per platform via `SENTRY_PROJECT` in eas.json platform env, auth token as EAS secret. Gotcha: the bare Sentry expo plugin hard-fails Xcode builds when unconfigured — one build lost, `SENTRY_ALLOW_FAILURE=true` since. Live log streaming via `enableLogs` + `consoleLoggingIntegration` — every `[VR]` line is now readable at Explore → Logs without a cable. This paid for itself the same hour.
- **Foreground reminders silent**: DELIVERED handler ran the Android cancel+repost lifecycle unguarded on iOS — it just ate the banner; plus `startAlarmAudioIfPossible` had a hard Android gate. Repost now Android-only (iOS keeps the delivered banner as the displayed alarm), audio gate opened, `foregroundPresentationOptions` explicit. `lib/notifications.ts`.
- **"Phone was just buzzing"**: `stopRecording()` reset the audio session with only `allowsRecordingIOS: false` — expo-av defaults `playsInSilentModeIOS` to false, flipping the whole app into mute-obeying mode after every recording. Voice was "playing" at inaudible volume. Fixed there + belt-and-braces re-assert (audio mode + `Sound.setCategory("Playback")`) before every alarm playback in `lib/AudioService.ts`.

Also: RevenueCat placeholder iOS key spams the Sentry stream (harmless, filter later); locked-screen notifications remained at iOS's mercy — which is what triggered the afternoon.

## Voice-as-alarm-sound: placed but not playing - (13:00-13:40)

**Status**: ⚠️ Alarm rings, but with the system default sound instead of the TTS line

First attempt: expo-file-system refused `makeDirectoryAsync` on `Library/Sounds` (scoped-directory sandbox, exactly AK-3's flagged risk). Fixed natively — `placeAlarmSound`/`removeAlarmSound` FileManager methods on the bridge, `lib/alarmSounds.ts` stages the wav in Documents then hands off. Build `fa0b096c`: tape shows `Alarm sound placed: reminder_m5brxdnjd.wav (141164 bytes)` and `sound_refreshed` with that name — but the alarm still rang default, and the phone auto-opened to Face ID → app on fire (unexpected; Done-tap behavior?).

Suspects, in order: (1) `AlertConfiguration.AlertSound.named()` may want the name WITHOUT the `.wav` extension; (2) creation double-schedules the same appKey ~20ms apart (two UUIDs — gap_resync racing the create path) and the stale default-sound alarm may be the one ringing; (3) wav format acceptance (22050 Hz mono PCM). The tape has everything needed to pin it.
