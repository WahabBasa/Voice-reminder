## Investigated duplicate repeating alarms + patched dedupe/lockscreen behavior - (11:04)

**Status**: OK - Reduced duplicate fires + prevented fallback UI latching on lockscreen

Observed issue on interval repeat reminders (ex: every 5 minutes):
- Sometimes 2 alarms fire at the same time.
- Dismissing the first on the lockscreen works, but a second alarm can keep playing or show UI later.
- In some cases the second "duplicate" shows no sound (only alarm screen), and only appears once the phone is unlocked.

What the logs showed:
- We often see both the trigger notification and our reposted "alarm_display_*" notification around the same time (expected).
- The problem case looks like multiple `reminder_{id}_*` triggers existing for the same reminder, causing true duplicate deliveries.
- The MainActivity fallback overlay can also "arm" while the device is locked and then surface later when the user unlocks.

Fixes applied:
- `lib/notifications.ts`:
  - Cancel any extra `reminder_{reminderId}_*` triggers before scheduling/rescheduling the next one (keep snooze triggers).
  - Ignore duplicate `DELIVERED` events for the same notification id (idempotent handling).
  - If an incoming delivery matches the active alarm's same `reminderId + scheduledFor`, ignore it instead of queueing.
- `app/_layout.tsx`:
  - If keyguard is locked, never show the MainActivity fallback overlay (primary path should be AlarmActivity).
  - Clear fallback overlay state using a functional state update to avoid stale closure issues.
