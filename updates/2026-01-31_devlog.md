## Follow-up: fixed repost loops + snooze payload gaps - (13:14)

**Status**: バ. Implemented guards/fixes, pending testing

Got reports that the “cancel + repost” strategy caused a runaway loop and that some alarms (esp snoozes) had missing fields:

- `DELIVERED -> displayNotification() -> DELIVERED -> ...` repeating thousands of times
- Snooze deliveries missing `audioUrl` / `frequency` so audio download fallback and reschedule logic couldn’t run
- Reposted `alarm_display_*` deliveries were still triggering navigation/audio work they weren’t meant to

### What changed (without claiming it’s fixed yet):

**1) Make reposted notifications display-only (`lib/notifications.ts`)**
- Added a stronger repost detector: `alarm_display_*` IDs OR `data.__reposted`
- Early-return for reposted deliveries so they don’t repost/reschedule/restart audio
- Repost IDs are now unique per occurrence: `alarm_display_${reminderId}_${scheduledFor}`

**2) Centralize displayed-alarm cleanup (`lib/notifications.ts`)**
- Added `cancelDisplayedAlarmNotifications()` and call it on:
  - `EventType.DISMISSED`
  - `EventType.ACTION_PRESS` (dismiss/snooze actions)

**3) Fix snooze created from AlarmScreen (`app/alarm.tsx`)**
- Snooze triggers now use `AlarmType.SET_ALARM_CLOCK` and `launchActivity = AlarmActivity`
- Snooze notification data now carries `audioUrl`, `frequency`, `time`, `days`, etc (pulled from deep-link params first, then store fallback)

**4) Pass required fields through deep-link (`index.ts`)**
- When navigating to `/alarm`, include `audioUrl/frequency/time/days/intervalDays` in query params so AlarmScreen can schedule snooze without depending on store hydration timing
- Ignore `DELIVERED` navigation for reposted `alarm_display_*` notifications

**5) Prebuild safety + Windows cleanup**
- `plugins/withFullScreenAlarm.js` now detects `.AlarmActivity` or the fully-qualified name to avoid duplicate injection
- Added `nul` to `.gitignore` since a reserved-name file was breaking `rg` scans on Windows
