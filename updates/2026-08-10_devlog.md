# Devlog - 2026-08-10

## AlarmKit foreground sound: diagnosed, it's iOS - (12:00)

**Status**: ⚠️ Apple's bug, not ours — mitigation scoped

Report: alarm fires while phone is in use → default timer tone; locked → voice plays fine. The sound is baked into the alarm at schedule time (`soundName` → `AlertSound.named`), so device state can't change what we passed — the divergence is inside iOS. Locked uses the full-screen alarm path (resolves our wav), attended uses the Live Activity banner path (fails to resolve `Library/Sounds`, silently falls back). Same bug family as FB19779004 on the Apple forums, unresolved since the betas. This clears the wav format, placement, hydration timing, and the dedup race as suspects.

Fixable slice: when *our* app is foreground, an `AlarmManager.alarmUpdates` observer can play the recording ourselves (CL-4, pending decision: voice-over-chime vs stop-and-replace). When the user is in another app, nothing app-side can help — that's an Apple Feedback filing.

## EAS Update lane: the 2-minute loop - (13:00-15:00)

**Status**: ✅ OTA updates working end to end

Network here is hostile (client isolation, ngrok blocked both attempts) so Metro can never reach the iPhone — which had the "just rewrite it in SwiftUI" idea gaining steam. Killed that with infrastructure instead: `expo-updates` installed, `eas update:configure`, one new dev build (`1be12e26`). JS changes now land on the phone in ~2 min over its own internet — `eas update --branch development --platform ios`. (`--platform ios` matters: no react-native-web, `--platform all` export fails.)

**Windows gotcha for the books**: export dies with `Failed to get the SHA-1 for ... require.js` when the shell's cwd has a lowercase drive letter. Publish via `powershell -Command "Set-Location C:\Dev\VR; npx.cmd eas-cli update ..."` — uppercase `C:` fixes it.
