# Devlog - 2026-02-01

## Moved alarm routing into RootLayout + persisted scheduledFor - (08:36)

**Status**: ⚠️ Still seeing main app UI on lockscreen alarms

Goal was to stop the alarm flow from ever launching the normal app UI (tabs/home) on the lockscreen, and to stop one-time alarms from looping/rescheduling as "now + 5s".

### What I changed

**1) Removed deep-link navigation from entrypoint (`index.ts`)**
The old approach used `Linking.openURL(voicereminder:///alarm?... )` from the JS entrypoint and/or AppState handlers. That was a big source of "AlarmActivity shows + MainActivity also opens" behavior.

- `index.ts` - removed alarm navigation; now only logs foreground events and calls `handleNotificationEvent()`

**2) Centralized alarm routing inside expo-router (`app/_layout.tsx`)**
Instead of navigating from `index.ts`, routing is now owned by `RootLayout` so it only happens once the router exists.

- Cold start: `notifee.getInitialNotification()` ƒÅ' persist pending alarm ƒÅ' route to `/alarm`
- Foreground delivered/press: listen in `_layout` and persist pending alarm, then route
- App foreground recovery: on `AppState` active, check pending alarm and route
- Added debug logs so it's obvious why routing is skipped (`inFlight`, `already_handled`, `reposted`, `alarm_display_*`, dedupe)

Key spots:
- `app/_layout.tsx:172` - `maybeRoute` debug logs (reason/inFlight/pending/skip)
- `app/_layout.tsx:226` - `maybeRoute2` debug logs (same, plus dedupe)

**3) Persist `scheduledFor` after scheduling**
This is to prevent the "once reminder fires -> restart -> startup sync sees no scheduled trigger -> reschedules -> time is in the past -> now + 5s -> repeats" loop.

- Voice-created reminders now store `scheduledFor` from `scheduleReminder()`:
  - `app/index.tsx:407` -> `triggerTimestamp` -> `updateReminder(...scheduledFor)`
- Manual reminders now store `scheduledFor` too:
  - `app/reminder/new.tsx:147`
- Edit/reschedule paths store `scheduledFor`:
  - `components/EditReminderSheet.tsx:323`
  - `components/EditReminderSheet.tsx:481`
- Startup sync also persists `scheduledFor` for reminders it auto-schedules:
  - `lib/notifications.ts:1004`

**4) Harden startup sync against resurrecting past-due one-time reminders (`lib/notifications.ts`)**
- If a one-time reminder is already past due, don't schedule it again (avoids "now + 5s" resurrection)
- If there's an unhandled pending alarm for that reminder, don't create a duplicate trigger

Key spots:
- `lib/notifications.ts:868` - reads pending alarm for skip logic
- `lib/notifications.ts:901` - skip duplicates if pending exists
- `lib/notifications.ts:914` - compute due time and skip if due <= now

**5) AlarmScreen close path tries to exit instead of showing home inside AlarmActivity (`app/alarm.tsx`)**
I added an Android-specific escape hatch so dismiss won't drop you back to the home screen UI inside the lockscreen activity.

- `app/alarm.tsx:145` - `BackHandler.exitApp()` when `!router.canGoBack()`

### What I saw in logs after these changes

- Audio still plays fine via native alarm stream (`AlarmAudioModule (USAGE_ALARM)`).
- Routing often doesn't happen because pending alarms are already marked handled:
  - `pending_get ... handledAt=...` then `maybeRoute2_skip reason=already_handled`
- Another failure mode: reposted notifications (`__reposted: "1"`) can launch full-screen, but routing currently skips reposted IDs by design, so you end up seeing the default app route (home/tabs) inside `AlarmActivity`.

### Current hypothesis (not fixed yet)
This is still an architectural mismatch:

- `AlarmActivity` loads the full RN app (`getMainComponentName() = "main"`), so the default route can show inside the lockscreen activity.
- If the notification that actually triggers the full-screen launch is a repost (`alarm_display_*` / `__reposted=1`), the router code intentionally skips routing it to `/alarm`.
- Dismiss/back behavior depends on whether `/alarm` was pushed/replaced and what the stack looks like, so it can still expose `/index` inside AlarmActivity.

## Added pending alarm state machine + AlarmOverlay fallback - (10:23)

**Status**: ƒsÿ‹÷? Alarm UI shows + dismiss stops audio, but dismiss still exposes main app UI underneath

This session was about fixing the “audio plays but alarm UI doesn’t show” bug by making the alarm UI independent of expo-router navigation. It’s improved: the alarm overlay now reliably appears and the dismiss button stops the alarm. But we still have a major UX issue: after dismiss, the underlying app UI (reminder create screen + bottom tabs/back buttons) becomes visible inside the same activity, which should not happen for a lockscreen alarm flow.

### What changed

**1) Pending alarm semantics split into explicit states (`lib/notifications.ts`)**
Replaced the old `handledAt` gate (which was blocking routing) with explicit fields:

- `ringingAt` (set when alarm audio successfully starts)
- `uiShownAt` (set when the UI actually mounts)
- `resolvedAt` + `resolvedAction` (set only when the user dismisses/snoozes)

This also includes a small migration that deletes legacy `handledAt` on read so old pending records don’t strand routing.

Key spots:
- `lib/notifications.ts:74` - new `PendingAlarm` shape
- `lib/notifications.ts:126` - legacy `handledAt` migration
- `lib/notifications.ts:162` - `alarm_state ringing_set`
- `lib/notifications.ts:178` - `alarm_state ui_shown_set`
- `lib/notifications.ts:194` - `alarm_state resolved_set`

**2) AlarmOverlay added as a “no-router-needed” UI fallback (`app/_layout.tsx` + `components/AlarmOverlay.tsx`)**
`RootLayout` now polls `getPendingAlarm()` every 1s and renders a full-screen overlay over the app stack whenever there’s an unresolved pending alarm.

This makes alarm UI show even if `/alarm` routing fails or expo-router starts on a default route.

Key spots:
- `app/_layout.tsx:415` - `checkAndShowAlarm` polling
- `app/_layout.tsx:436` - `overlay_show` log
- `app/_layout.tsx:422` - `overlay_hide` log
- `components/AlarmOverlay.tsx:96` - `alarm_overlay_mount`
- `components/AlarmOverlay.tsx:102` - marks `uiShownAt` on mount

### What I saw / current behavior

- Alarm overlay now appears and audio plays fine via `AlarmAudioModule (USAGE_ALARM)`.
- Dismiss stops audio and clears the pending alarm correctly:
  - `alarm_state resolved_set ... action=dismiss`
  - `pending_clear`
- However, after dismissing, the normal app UI becomes visible (reminder creation screen + bottom navigation/back buttons).
- You also reported the alarm screen/overlay showing an error mentioning “PUSH” on appearance.
- Flow you observed:
  1) Alarm shows (with PUSH error)
  2) Tap Dismiss → you’re taken to the reminder creation page (should not be visible)
  3) Tap Back → returns to the alarm page
  4) Tap Dismiss again → returns to lock screen

### Current hypothesis (not solved yet)

We’re still not reliably closing/finishing the lockscreen `AlarmActivity` after dismiss/snooze.

Right now the overlay decides whether to exit based on a JS heuristic (`shouldExitOnResolve`). When it decides “normal app use”, it logs:
- `close_alarm_overlay action=none (normal app use)`

That causes the overlay to unmount and reveal whatever expo-router rendered underneath inside the same activity (tabs + reminder create). That matches the symptom.

The “PUSH” error likely indicates expo-router navigation is still happening (or attempted) at the same time as the overlay lifecycle, which may explain why hitting back brings you to an alarm page route.

### Files touched (this session)
- `lib/notifications.ts` - new pending alarm state fields + migration + resolved/ringing/uiShown markers
- `app/_layout.tsx` - alarm overlay polling + show/hide logic
- `components/AlarmOverlay.tsx` - full-screen alarm UI (dismiss/snooze + marks uiShownAt)

### Next steps (for next session)
1. Make “lockscreen alarm mode” detection reliable and deterministic (JS heuristics are not enough).
2. On dismiss/snooze in lockscreen mode: finish/close `AlarmActivity` so the main app UI never becomes visible.
3. Capture the exact “PUSH” error text/stack (it likely points to where router navigation is still occurring) and remove/guard that navigation during alarm mode.
