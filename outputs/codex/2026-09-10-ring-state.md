**(2) Root causes of each symptom**

- **Immediate overdue:** confirmed in an in-memory replay of the actual resolver: before trigger → “Next in 1 min”; at trigger/+1 second → “Overdue”; snooze snapshot supplied → “Rings again”; snooze expires → original overdue time returns. A daily repeater instead showed tomorrow at its trigger. The implementation has neither active-occurrence identity nor ringing input. - **Later updates late:** foreground reconciliation and the card refresh run independently. The card can read storage before reconciliation writes it, then wait another tick. If an intent runs while JS remains foregrounded without an AppState transition, the tick only rereads AsyncStorage—it does **not** drain native events. Therefore the delay is not necessarily bounded by 30 seconds. **(4) Proposed fix, reasoning and trade-offs**

- **Introduce persisted occurrence lifecycle, not just `lastRingResolvedAt` on the reminder.** Key it by reminder + scheduled occurrence + native alarm identity, retaining comeback origin. This avoids one ring overwriting another on multi-time reminders; existing `nagOrigins` already demonstrates that requirement. Derive card presentation from it while retaining the existing schedule resolver. [lib/notifications.ts:1414](/C:/Dev/VR/lib/notifications.ts:1414)
- **Observe actual native state.** Add an initial AlarmManager snapshot and `alarmUpdates` subscription; persist intent outcomes and notify active JS after writes. Foreground recovery should load reminders, reconcile native evidence, then publish one card snapshot. A notification is a wake-up hint, not the durable record. This requires native implementation and a new binary, beyond an OTA-only card change. [docs/alarmkit-focus-breakthrough.md:206](/C:/Dev/VR/docs/alarmkit-focus-breakthrough.md:206), [plugins/withAlarmKit.js:738](/C:/Dev/VR/plugins/withAlarmKit.js:738); [Apple alarm updates](https://developer.apple.com/documentation/alarmkit/alarmmanager/alarmupdates-swift.property).
- **Freeze the ringing occurrence’s card presentation and ordering until resolution.** Apply this to repeaters and snooze comebacks too. Do not call elapsed scheduled time “confirmed ringing” when authorization/delivery is absent, and do not invent a 60–120-second AlarmKit timeout. An unresolved/unknown state is more honest than false completion or false “Missed.” [lib/remindersMembership.ts:38](/C:/Dev/VR/lib/remindersMembership.ts:38), [lib/alarmKit.ts:463](/C:/Dev/VR/lib/alarmKit.ts:463)
- **Publish the actual armed next time immediately after successful Later/reschedule.** Keep the native race guard first, but separate it from the displayed comeback time; handle exhausted caps and failed registration without claiming another ring exists. Share the reactive snapshot with fallback handlers. Existing detached scheduling suppresses errors, so merely writing a timestamp earlier is insufficient. [plugins/ios-src/VRAlarmIntents.swift:530](/C:/Dev/VR/plugins/ios-src/VRAlarmIntents.swift:530), [plugins/ios-src/VRAlarmIntents.swift:595](/C:/Dev/VR/plugins/ios-src/VRAlarmIntents.swift:595), [plugins/withAlarmKit.js:508](/C:/Dev/VR/plugins/withAlarmKit.js:508)
- **Unify Done by occurrence across system Stop, overlay, notification action and card.** Stop/cancel that ring and its comeback chain, publish completion promptly, retain future repeater occurrences. Make reconciliation idempotent and acknowledge events only after durable application: today the native drain deletes first, and even a `pending` outcome is then discarded. [app/index.tsx:1657](/C:/Dev/VR/app/index.tsx:1657), [lib/notifications.ts:1521](/C:/Dev/VR/lib/notifications.ts:1521), [plugins/withAlarmKit.js:362](/C:/Dev/VR/plugins/withAlarmKit.js:362), [lib/notifications.ts:1979](/C:/Dev/VR/lib/notifications.ts:1979)
- **Treat “Missed · time” as presentation of an unanswered ring, not completion.** If another comeback is armed, also show its actual next time. Final missed history currently waits for chain exhaustion; changing that ledger policy would be a separate decision. [lib/notifications.ts:2055](/C:/Dev/VR/lib/notifications.ts:2055), [lib/notifications.ts:2094](/C:/Dev/VR/lib/notifications.ts:2094)

**(5) What NOT to change, and why**

- **Do not promise X → tick on the iOS 26.6 system alert.** Stop appearance is system-controlled; its completion behavior is already wired and needs reliable propagation. Replacing the foreground surface requires a separate native stop-and-custom-UI/audio design. - **Keep snooze-nag policy and race guards:** same recording, five-minute cadence, at most three comebacks; no escalation resurrection or unlimited persistence. Preserve guard-before-stop and background intents, which protect Later and lock-screen operation without Face ID.
