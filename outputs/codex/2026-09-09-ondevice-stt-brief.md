## Plan
A. **Native module `VRSpeech` (Swift, iOS 26+, same injection pattern as AlarmKit, classic bridge)**. Phase 1 is FILE-BASED, not streaming: keep expo-av recording exactly as is (VoiceMeter, permission, 16 kHz preset untouched); on stop, call `VRSpeech.transcribeFile(uri, localeId)` which runs `SpeechAnalyzer` + `SpeechTranscriber` over the m4a via `AVAudioFile` and resolves `{ text, localeId, ms }`. Plus `VRSpeech.status(localeId)` → `{ available: boolean, installed: boolean, reason }` and `VRSpeech.prepare(localeId)` which reserves/downloads the locale assets (`AssetInventory`) — called at app start / after mic consent so first take is not blocked by a model download. Below iOS 26 or when unavailable → module reports unavailable and the client uses the cloud path unchanged.
B. **Backend**: `creationJobs.begin` accepts `transcript?: string` with `audioStorageId?` now optional (exactly one required). Worker: when `transcript` present, skip storage get + STT, CAS straight to `transcribed`, parse as today. Perf: add `sttSource: "device" | "cloud"` and `deviceSttMs` to the job perf; `stt_perf` line skipped for device. Job table gets `transcript`/`sttSource` fields (schema additive). Retry/reconcile untouched. Keep the audio upload happening in parallel (fire-and-forget) for the first release so a bad on-device transcript can be compared against cloud in logs? — see Q4.
C. **Client** (`app/index.tsx` handoff + `lib/voiceTake.ts`): on stop, if VRSpeech available for the chosen locale → transcribe file (device timing logged as `[VR PERF] device_stt`), then `begin({transcript})`; if transcription throws / returns empty / times out (3 s cap) → fall back to the existing upload+begin path with the same creationId. Locale: new setting "Voice language" (English / Arabic) defaulting from the device locale, stored locally; passed as localeId. 
D. **Build**: native → new EAS build (build 3 is already planned for the 2.1 resubmission), then OTA for JS iterations.
E. **Split for parallel agents**: (1) native module + plugin + JS wrapper with a typed contract, (2) backend begin/worker/schema/tests, (3) client integration + fallback + setting + tests — contracts defined up front so all three can run concurrently; then a build + device-verify step.
