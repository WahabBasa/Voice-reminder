Only after some time does the state update to show when it should next ring. ## Claude's initial reasoning for the fix (grill it)
- The card derives "Overdue" purely from `now > nextRing` with no notion of "currently ringing". Proposed: a ringing window — from the scheduled trigger until the ring resolves (Stop/Done, Snooze, or a max ring duration, e.g. AlarmKit's own timeout or a fixed 60-120 s for the fallback) — during which the card keeps showing the pre-ring state ("Now" / "Ringing"), not "Overdue". Persist the resolution (`lastRingResolvedAt`, outcome) on the reminder so a relaunch computes the same thing.
- Snooze must write the new next-ring time to the store synchronously in the same handler that arms the snooze, and trigger the list refresh — not wait for the 30 s tick. If the Snooze happens in the AlarmKit intent (extension/system process) while the app is suspended, the app must reconcile on next foreground from a persisted source (App Group / UserDefaults / the AlarmKit alarm's state) — find what exists.
- The X → tick: if the surface is AlarmKit's system alert, Apple defines the button set (Stop + optional secondary); we can relabel/re-icon Stop as Done with a checkmark if the API allows (check `AlarmButton` in the generated Swift), and Stop should mark the reminder done (one-off) or advance it (repeater), not leave it "overdue". If it is our own in-app overlay/banner, we own it fully.
- "Timed out" ring (ignored): after the window, it IS overdue — that's the honest state — but the card should say "Missed · 3:52 pm" rather than an alarming red the instant the ring starts.
- What should NOT change: the nag/persistent semantics (CL-4 decision: no escalation, snooze-nag instead), the OLD-110/111 lock-screen Done-without-Face-ID behavior, the AlarmKit sound pipeline.
